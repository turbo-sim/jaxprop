# JaxProp uniform fluid interface implementation plan

**Publication update, 15 November 2026:** JaxProp 0.6.0 is tagged and published on PyPI following the user's explicit release instruction. Hosted Linux and Windows HEOS release gates passed. Barotropy verification completed with 271 passing tests against the published wheel; its dependency floor is now 0.6.0. ThermOpt work in Phase 15 remains separately open. Earlier preparation and measurement checkpoints below retain their historical scope.

Uniform, consistent behavior across fluid objects is the primary goal. Backward compatibility is secondary. The implementation should protect valid physical calculations while establishing consistent construction, property calls, identity, array shapes, reference metadata, capabilities, and errors.

This checklist starts from the local 0.5.8 source at commit `ed66d108555e71d0d8543a1b670d05237a834221`, reviewed on 12 November 2026. The [native JAX efficiency audit](z_JAX_EFFICIENCY_AUDIT.md), added on 13 November 2026, records compiler/source inspection, implemented execution/state fixes, and larger optimization ideas assigned to the phases below.

A phase is complete when its checklist is complete.

Implement and verify one coherent change at a time. Start with tests for its intended behavior, implement the change, run the affected tests, and then run the shared contract/numerical checks relevant to its callers. Use the full HEOS suite at the phase boundaries. Run the declared optional-backend and slow integration cases before completing their corresponding release scope. Revisit completed items when a later change alters their contract.

Preserve useful source docstrings, scientific derivations, units and algorithm rationale throughout the refactor. Move explanations with the code they describe and document new setup options. Keep functions and names readable; performance work should remove redundant numerical work and data handling, rather than shorten source explanations. Remove obsolete/debug commentary when its underlying implementation is removed.

## Interface consistency and runtime budget

Keep common syntax and declared behavior consistent without adding numerical work merely for API presentation. Validate method/backend/options and prepare immutable source data once at construction; do not rediscover capabilities, source versions or reference fingerprints in repeated native evaluations. Compute optional diagnostics only when requested. Required numerical failure checks must be fused with existing array/batch work, not repeated per property; retain correctness and measure their real cost rather than promising unmeasured zero overhead. Native PG/bicubic execution, transformed consumers and source/callback calls have separate timing records.
